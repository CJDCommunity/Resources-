Part 1 — Core Production Debugging Scenarios

Q1

API latency suddenly increases after deployment. What do you check first?

Example

You deploy v2.3 of an order service at 2 PM. By 2:15 PM, p95 latency jumps from 200ms to 2s.

Approach
  • Overlay the deployment marker on your APM latency graph — confirm the spike aligns with the deploy, not a coincidental traffic spike.
  • Diff the release (git diff v2.2..v2.3) for new DB queries, added synchronous external calls, or changed serialization logic.
  • Check DB slow query logs for anything new appearing post-deploy.
  • If unclear, roll back immediately to restore service, then investigate in a lower environment with production-like data volume.
Root Cause

A new field on the response DTO triggered a lazy-loaded JPA relationship on every request — turning 1 query into 1+N queries.

Fix

Use @EntityGraph or an explicit JOIN FETCH to eagerly load only what's needed, and add a regression test asserting query count for that endpoint.

Q2

Database connection pool gets exhausted. What could be the reason?

Example

HikariCP pool size is 20. During a traffic burst you see Connection is not available, request timed out after 30000ms.

Approach
  • Check Hikari metrics: active, idle, pending. If active is pinned at max and pending grows, the pool is starved.
  • Take a thread dump and inspect threads WAITING on Hikari — are they stuck in a long query or waiting on an external call while holding a connection?
  • Look for connections opened outside try-with-resources, or a session never closed.
Root Cause

A batch export endpoint held a DB connection open for the entire duration of streaming a large CSV to the client — concurrent exports drained the pool fast.

Fix

Fetch data, close the connection, then stream. Also enable leak detection:

spring:
  datasource:
    hikari:
      leak-detection-threshold: 30000
      maximum-pool-size: 20

Q3

API works locally but becomes slow in production. How do you debug it?

Example

A search endpoint returns in 50ms locally but takes 3s in prod.

Approach
  • Compare data volume — 500 rows locally vs 5 million in prod. Run EXPLAIN ANALYZE on the exact prod query.
  • Check whether an index that exists locally is missing in prod, or vice versa.
  • Check network hops — localhost DB vs cross-AZ calls in prod.
  • Check prod logging level — verbose DEBUG logging with object serialization can silently add hundreds of ms.
Root Cause

The WHERE clause applied a function on an indexed column (WHERE LOWER(email) = ?), preventing index use at scale — invisible locally on a tiny table.

Fix

Add a functional index (CREATE INDEX ON users (LOWER(email))) or normalize data on write instead of filtering with a function.

Q4

A Spring Boot service starts returning random 500 errors. Where do you begin?

Example

~2% of requests to /checkout fail with a generic 500 and no obvious pattern.

Approach
  • Add a global exception handler if missing, so every 500 logs the full stack trace with a correlation ID.
  • Search logs by correlation ID to see the exact exception, not just "500 returned."
  • Check whether failures correlate with a specific payload shape, user segment, or time window.
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleGeneric(Exception ex, HttpServletRequest req) {
    log.error("Unhandled exception, traceId={}", MDC.get("traceId"), ex);
    return ResponseEntity.status(500).body(new ErrorResponse("Internal error", MDC.get("traceId")));
}
Root Cause

A NullPointerException on order.getDiscount().getCode() — discount was null for orders without a promo, and a recent change stopped guarding for that.

Fix

Add null-safety (Optional, defensive checks), plus a unit test for "no discount applied," and add contract tests for optional fields.

Q5

Memory usage keeps increasing until the application crashes. How do you find the root cause?

Example

A Spring Boot service's heap climbs steadily over 6 hours and then OOMs.

Approach
  • Enable heap dump on OOM: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps
  • Take periodic dumps (jmap -dump:live,format=b,file=heap.hprof <pid>) to compare growth over time.
  • Load into Eclipse MAT, run "Leak Suspects Report," and inspect the dominator tree.
  • Check GC logs (-Xlog:gc*) — if old-gen never drops after a full GC, it's a real leak.
Root Cause

A static Map<String, List<Event>> used as an in-memory cache with no eviction policy grew unbounded as new event types were added.

Fix 
Cache<String, List<Event>> cache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(30))
    .build();

Q6

One downstream service becomes slow and affects your entire API. How would you isolate the impact?

Example

order-service calls payment-service. Payment starts responding in 15s instead of 200ms, and threads pile up until the entire API becomes unresponsive — even endpoints unrelated to payments.

Approach
  • Confirm the correlation via a thread dump — are threads stuck WAITING/TIMED_WAITING on the payment client call?
  • Check whether a timeout is configured at all — often the bug is "no timeout set," so it waits indefinitely.
Fix 
@CircuitBreaker(name = "paymentService", fallbackMethod = "fallbackPayment")
@TimeLimiter(name = "paymentService")
public CompletableFuture<PaymentResponse> callPayment(PaymentRequest req) {
    return CompletableFuture.supplyAsync(() -> paymentClient.charge(req));
}

Also use a bulkhead (a separate thread pool) for the payment-service call so it can't starve threads used by unrelated endpoints.

Q7

Multiple users update the same record simultaneously. How do you prevent inconsistent data?

Example

Two support agents open the same ticket and update its status at the same time — one update silently overwrites the other (the "lost update" problem).

Approach

Decide whether the case needs optimistic or pessimistic concurrency control based on contention frequency.

Fix

Optimistic locking (most common):

@Entity
public class Ticket {
    @Version
    private Long version;
}

A racing second update throws OptimisticLockException → return 409 Conflict telling the agent to refresh and retry.

Pessimistic locking for high-contention resources (e.g., inventory decrement during a flash sale):

SELECT * FROM inventory WHERE product_id = ? FOR UPDATE;

Q8

Cache improves performance but starts serving stale data. How would you fix it?

Example

A product price updates in the DB, but the API keeps returning the old price for up to 10 minutes because of a Redis cache with a 10-minute TTL.

Approach
  • Confirm it's the cache, not replication lag, by checking Redis directly vs the DB value.
  • Decide: is short staleness acceptable (TTL-only is fine), or does this need strong consistency (needs invalidation)?
  • Check the cache key — if it's inconsistent, one part of the app updates one entry while another reads a different one.
Fix

Move from pure TTL to cache-aside with explicit invalidation on write:

@Transactional
public void updatePrice(Long productId, BigDecimal newPrice) {
    productRepository.updatePrice(productId, newPrice);
    redisTemplate.delete("product:" + productId); // evict on write
}

For multi-instance setups, publish an invalidation event (Redis Pub/Sub or Kafka) so all instances evict local caches, not just the shared Redis layer. Spring alternatives: @CacheEvict to remove, @CachePut to refresh in place — always keep the cache key consistent between read and write paths.

Q9

Your scheduled job executes multiple times after deploying multiple instances. Why?

Example

A @Scheduled daily billing job runs at midnight. After scaling from 1 to 3 instances, customers get billed 3 times.

Approach

This is expected once you understand it: each instance runs its own in-process scheduler independently, unaware of the others.

Fix

Use ShedLock so only one instance executes at a time:

@Scheduled(cron = "0 0 0 * * *")
@SchedulerLock(name = "dailyBilling", lockAtMostFor = "PT30M", lockAtLeastFor = "PT5M")
public void runDailyBilling() {
    billingService.processDailyBilling();
}

This uses a shared DB/Redis table as the lock coordinator. For heavier needs, move scheduling out of the app entirely (Quartz with a JDBC job store, or an external orchestrator like Airflow / AWS EventBridge triggering a single Lambda).

Q10

Application is healthy, but users are still getting timeouts. What would you investigate?

Example

Health checks return 200 OK, CPU/memory look normal, but users report intermittent timeouts.

Approach
  • Check the load balancer / ingress layer — connection queue depth, backlog, 5xx rates at the LB, not just the app.
  • Check if the client-side timeout is simply too aggressive relative to actual p99 under load.
  • Check the app's thread pool queue length (e.g., Tomcat's accept-count) — requests may queue for a worker thread even while CPU is idle.
Root Cause

Tomcat's max-threads was set too low relative to real concurrency, so requests queued and timed out at the LB before reaching an app thread — app-level metrics looked "healthy" because the requests never got that far.

Fix

Tune server.tomcat.threads.max and accept-count based on load testing, and monitor queue depth as its own metric, not just CPU/memory.

Q11

API response is slow even though the database query is fast. Where else could the bottleneck be?

Example

DB query takes 20ms per EXPLAIN ANALYZE, but the endpoint takes 800ms end-to-end.

Approach

Instrument each phase of the request (deserialization → business logic → DB call → serialization → external calls) instead of assuming the DB is the bottleneck.

Root Cause

The response DTO triggered lazy loading of a collection with 200 related entities, each requiring a separate query — the "20ms" measured was just the first query, not the hidden N+1 chain behind Jackson serialization.

Fix

Use JOIN FETCH or a dedicated projection/DTO query. Catch this earlier by enabling Hibernate statistics in staging:

spring:
  jpa:
    properties:
      hibernate:
        generate_statistics: true

Q12

Logs are available across services, but tracing one request is difficult. What would you implement?

Example

A user reports "my order failed," but you have separate logs for api-gateway, order-service, inventory-service, and payment-service, with no way to connect them.

Approach & Fix

Implement distributed tracing with a propagated trace ID:

// Filter that generates/propagates trace ID
String traceId = request.getHeader("X-Trace-Id");
if (traceId == null) traceId = UUID.randomUUID().toString();
MDC.put("traceId", traceId);

Pass X-Trace-Id downstream on every outbound call, and log it via MDC everywhere. For full visibility, adopt OpenTelemetry to get automatic spans across HTTP, DB, and messaging calls — visualized in Jaeger, Zipkin, or Grafana Tempo. Centralize logs (ELK/Loki) with trace ID as a searchable field, so tracing an order becomes one query: traceId=abc123.

Q13

Traffic suddenly increases 10x. What would you check before simply adding more servers?

Example

A marketing campaign drives 10x normal traffic in an hour.

Approach
  • Identify the actual constraint first — CPU, DB connections, or a downstream rate limit. Scaling app servers won't help if the DB is the bottleneck; you'll just exhaust the connection pool faster with more instances.
  • Check whether it's genuine user traffic or a retry storm from an upstream failure amplifying load artificially.
  • Check cache hit rate — a drop means the cache layer is undersized for the new pattern.
Fix

Scale horizontally and add a read replica or connection pooler (PgBouncer). Add rate limiting at the edge to shed excess load gracefully (429s instead of timeouts). Ensure autoscaling targets request-based metrics, not just CPU, since I/O-bound services often stay CPU-cool under load.

Q14

Application works perfectly in staging but fails in production. What differences would you compare?

Example

A payment integration works flawlessly in staging but fails silently in prod.

Approach
  • Config/secrets: staging often points to a sandbox key vs prod's live key with different rate limits or stricter validation.
  • Data shape: staging has clean, minimal test data; prod has years of legacy edge cases.
  • Scale: race conditions may never trigger in staging's low traffic.
  • Network: staging might allow all outbound calls; prod may block some via security groups.
Root Cause

The prod third-party payment API enforced strict idempotency-key validation, but staging's sandbox didn't — a bug generating duplicate idempotency keys never surfaced until prod.

Fix

Make staging match prod as closely as possible (same API tier, similar data volume via anonymized prod data), and add contract tests against the real sandbox with production-like validation rules.

Q15

A service crashes only under heavy load. How would you identify the actual root cause?

Example

A service runs fine normally but crashes with OutOfMemoryError or hangs entirely during a load test or traffic spike.

Approach
  • Reproduce deliberately with a load testing tool (k6, Gatling) against staging, ramping up while watching metrics.
  • Take a thread dump right before the crash (not after) — script a trigger that captures jstack when CPU/memory crosses a threshold.
  • Look for thread pool queue overflow, deadlocks, or synchronous blocking calls inside a loop that don't scale.
Root Cause

A synchronized method around an in-memory rate limiter became a massive contention point — under low load it was invisible, but under heavy load nearly every thread queued for that single lock, cascading into thread pool exhaustion.

Fix

Replace the coarse synchronized block with a lock-free structure (AtomicInteger, ConcurrentHashMap) or a distributed rate limiter (Redis + Lua script) that doesn't serialize all threads through one JVM-level lock.

Part 2 — Spring Boot & Microservices Design Scenarios

Q16

Application is fine under normal traffic but becomes very slow under high traffic. How will you find the root cause?

Example

A flash-sale event drives traffic 5x normal, and p95 latency climbs from 300ms to 4s while error rates stay low.

Approach
  • Don't jump into changing code — first localize where the slowness comes from: application logs, API response time, DB query time, memory/CPU usage, and thread usage.
  • Use Spring Boot Actuator, Grafana, a profiler, or Splunk to correlate metrics with the load spike.
  • If the DB is slow, optimize queries or add indexes. If the same data is fetched repeatedly, add caching. If an external API is slow, add timeout, retry, and a circuit breaker. If it's genuinely capacity, plan to scale.
Fix

Usually a combination: add a covering index for the hot query, wrap the read path in @Cacheable, and add Resilience4j timeouts around any external dependency in the request path.

Q17

You added @Transactional, but data is still partially saved when an exception happens. How will you debug and fix it?

Example

An order-placement method saves the order header but not the order lines when a downstream validation throws a checked InventoryException.

Approach
  • Confirm @Transactional is on the service layer method (not the repository or controller).
  • Check the exception type — Spring rolls back by default only for unchecked exceptions (RuntimeException). A checked exception won't trigger rollback unless told to.
  • Check the method isn't private — Spring's proxy-based AOP can't intercept private methods.
  • Check it isn't being called from within the same class (self-invocation bypasses the proxy entirely).
Fix 
@Transactional(rollbackFor = Exception.class)
public void placeOrder(OrderRequest req) throws InventoryException {
    // ...
}

And move self-invoked transactional methods into another Spring bean, or inject a self-reference, so the proxy is actually used.

Q18

One microservice calls another via REST, but the second service is sometimes slow or down. How will you handle timeout, retry, and fallback?

Example

order-service calls inventory-service to check stock; inventory occasionally takes 10s+ to respond during its own GC pauses.

Approach
  • Set a proper timeout so the caller never waits indefinitely.
  • Retry only for transient failures, with a capped retry count and exponential backoff (to avoid amplifying load on an already struggling service).
  • Add a fallback: a default response, a cached response, or a clear error message.
Fix

Use Resilience4j for timeout, retry, circuit breaker, and fallback together, e.g. @CircuitBreaker + @Retry + @TimeLimiter stacked on the client call, with a fallback method that returns cached stock levels.

Q19

A JWT token is still valid, but the user's role changed in the database. How do you make sure old permissions aren't misused?

Example

A user is demoted from ADMIN to VIEWER at 10:00 AM, but their JWT (issued at 9:00 AM, valid until 11:00 AM) still carries the ADMIN role claim.

Approach

JWTs are stateless by design, so a role change doesn't automatically invalidate an issued token. Mitigate with:

  • Short access-token expiry (10–15 minutes), paired with a refresh token flow.
  • For sensitive APIs, re-check the latest role from DB/cache rather than trusting the token claim blindly.
  • Token versioning: keep a token version per user in the DB. Bump it whenever the role changes; reject any token carrying an older version.
Fix

Store tokenVersion on the user record and embed it as a claim. On each request, compare the claim to the current DB value in a lightweight cache-backed check — mismatch means "reject and force re-login."

Q20

Database queries are increasing suddenly because of the N+1 query problem. How will you detect and solve it?

Example

An endpoint listing 50 users fires 51 queries: one to fetch users, then one per user to lazily fetch their orders.

Approach
  • Enable SQL logging and count queries per API call.
  • Confirm the pattern: one query for the parent, then N queries for child collections triggered by lazy loading.
Fix

Use JOIN FETCH, @EntityGraph, or a custom projection query to fetch everything needed in one round trip. Re-check SQL logs afterward to confirm the query count dropped.

Q21

One API is throwing LazyInitializationException in production. How will you identify and fix it?

Example

An endpoint fetches an Employee inside a transaction, returns it, and a serializer later tries to access the lazy department field after the Hibernate session has already closed.

Approach
  • Identify which lazy field triggers the exception from the stack trace.
  • Fetch the needed data inside the transaction, not after it.
Fix

Use JOIN FETCH or @EntityGraph to eagerly load exactly what's required, or map to a DTO with only the needed fields inside the transactional method. Avoid making everything EAGER globally — that trades this bug for a performance problem.

Q22

Messages from Kafka or RabbitMQ are processed twice. How will you handle duplicate processing?

Example

A payment-processing consumer receives the same PAYMENT_INITIATED event twice after a broker rebalance, and charges the customer twice.

Approach

Accept that at-least-once delivery means duplicates will happen — the fix is making the consumer idempotent, not preventing redelivery.

Fix

Attach a unique message/transaction ID to every message. Before processing, check if that ID was already handled; if so, skip it:

if (processedIdRepository.existsById(event.getMessageId())) {
    return; // already processed, skip
}
processPayment(event);
processedIdRepository.save(new ProcessedId(event.getMessageId()));

This is critical for payments, orders, and notifications where duplicates cause real business damage.

Q23

A microservice publishes an event, but the consumer service is down at that time. How do you make sure the event isn't lost?

Example

order-service publishes ORDER_PLACED, but notification-service is mid-deployment and temporarily unavailable.

Approach

Decouple producer and consumer entirely via a message broker (Kafka/RabbitMQ) instead of a direct call. The producer publishes to the broker regardless of consumer availability; the message persists in the topic/queue until read.

Fix

In Kafka, consumer offsets track what's been processed so a restarted consumer resumes where it left off. In RabbitMQ, use acknowledgments to confirm processing. If processing keeps failing, route to a dead letter queue instead of dropping the message, and alert on DLQ growth.

Q24

You have two implementations of the same interface, and Spring is confused about which bean to inject. How will you solve this?

Example

Both CreditCardPaymentService and UpiPaymentService implement PaymentService, and a plain @Autowired PaymentService paymentService fails to start with NoUniqueBeanDefinitionException.

Approach

Spring found more than one bean of the same type and can't pick automatically — you need to disambiguate explicitly.

Fix 
@Autowired
@Qualifier("upiPaymentService")
private PaymentService paymentService;

If one implementation should be the default in most places, mark it @Primary instead, and reserve @Qualifier for the specific overrides.

Q25

Actuator is enabled in production, but you don't want everyone to access health, metrics, or environment details. How will you secure it?

Example

/actuator/env is publicly reachable and leaks datasource URLs and internal config to anyone who hits the endpoint.

Approach
  • Don't expose all Actuator endpoints publicly — endpoints like /actuator/env, /actuator/beans, and /actuator/configprops can leak sensitive details.
  • Expose only what's needed publicly — usually /actuator/health and /actuator/info.
Fix

Secure the rest behind Spring Security with a dedicated role (e.g. ACTUATOR_ADMIN), restrict access to admin users or monitoring tools only, and enforce HTTPS throughout.

Q26

Secret keys and database passwords shouldn't live in application.properties. How will you manage them securely?

Example

A prod DB password is committed directly into application-prod.properties in the repo — visible to anyone with repo access.

Approach

Never hardcode credentials in code or config files. Keep non-sensitive config in properties/YAML, but source sensitive values from outside the codebase.

Fix

Use environment variables, Spring Cloud Config Server, or a dedicated secret manager — HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, or Kubernetes Secrets. The application reads secrets at runtime, which also makes rotating secrets possible without a code change.

Q27

Authentication is handled by one service, but other services also need to know if the user is valid. How will you design security?

Example

auth-service handles login; order-service, catalog-service, and payment-service each need to know the caller is authenticated and what role they hold.

Approach

Centralize authentication in one service. On successful login, issue a JWT containing user ID and roles. Every downstream request carries this token.

Fix

The API Gateway validates the token first; downstream services can independently validate it too and make authorization decisions based on the embedded role claims — no service needs to re-authenticate the user. Use HTTPS everywhere, and add service-to-service authentication (mTLS or a service mesh) for internal calls if needed.

Q28

Your application calls three external APIs, and one has rate limits. How do you avoid crossing the limit while staying stable?

Example

A geocoding API allows only 100 requests/minute, but your app calls it on every checkout to validate an address.

Approach
  • Understand the exact limit (requests per minute/second) and enforce it client-side before you hit it externally.
  • Cache data that doesn't change frequently to cut unnecessary calls.
  • Retry only on transient failures, with exponential backoff — never retry aggressively.
Fix

Add client-side rate limiting with Bucket4j or Resilience4j's RateLimiter, and return a fallback/queued response when the limit is reached instead of letting the external API block or ban your app.

Q29

One API fetches the same master data again and again from the database. How will you use caching to improve performance?

Example

An address form calls the "country list" endpoint on every page load, hitting the DB for the same ~200 rows thousands of times a day.

Approach

Identify data that's read often but changes rarely — country/state/city lists, product categories, configuration data — and cache it.

Fix 
@EnableCaching
// ...
@Cacheable("countries")
public List<Country> getCountries() {
    return countryRepository.findAll();
}

First call populates the cache from the DB; subsequent calls read from cache. If master data changes, evict or refresh it with @CacheEvict or @CachePut rather than waiting for TTL expiry.

Q30

One API returns thousands of records and the frontend becomes slow. How will you implement pagination and sorting?

Example

A /products endpoint returns all 50,000 rows in one response, and the browser tab freezes rendering the table.

Approach

Never return everything at once. Have the frontend send page number, page size, sort field, and sort direction, and let the backend return only what's needed.

Fix 
@GetMapping("/products")
public Page<Product> getProducts(
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "20") int size,
        @RequestParam(defaultValue = "name") String sort) {
    Pageable pageable = PageRequest.of(page, size, Sort.by(sort));
    return productRepository.findAll(pageable);
}

Spring Data JPA returns only the requested slice, plus total record and page counts for the frontend to build a paginator.

Q31

You have different database URLs for dev, QA, and production. How will you manage this without changing code every time?

Example

The dev DB is a local Postgres instance; QA points to a shared test cluster; prod points to an RDS instance with different credentials entirely.

The code stays identical across environments — only configuration changes.

Q32

Users upload PDF or image files. How will you handle file upload, validation, storage, and retrieval?

Q33

Uploaded files are stored inside the application server folder, and files disappear after deployment. What will you change?

Example

Profile pictures saved to /app/uploads/ on the server vanish the moment the container is redeployed, since the filesystem is ephemeral.

Root Cause

Storing files inside the app server's local filesystem breaks on redeploy (folder gets replaced) and doesn't work across multiple instances (a file uploaded to instance A won't exist on instance B).

Fix

Move storage outside the application entirely — AWS S3, Azure Blob, Google Cloud Storage, or a shared network filesystem. Keep only the file's metadata in the database, and reference the actual file by its external URL/path. This makes storage safe across redeployments and scalable across instances.

Q34

You need to send a welcome email after registration, but it shouldn't slow down the registration API. How will you design this?

Example

The SMTP provider occasionally takes 3–4 seconds to accept a message, which would otherwise make every signup feel sluggish.

Approach

Complete and persist the registration first, and never make the user wait on email delivery.

Fix

Simple approach — run email sending on a separate thread:

@Async
public void sendWelcomeEmail(User user) {
    emailClient.send(user.getEmail(), "Welcome!");
}

Better approach for reliability — publish a USER_REGISTERED event to Kafka/RabbitMQ, and have a separate email service consume it and send the email. If the email service is slow or down, registration itself never fails.

Q36

Your application needs to support multiple languages, like English and Hindi. How will you implement internationalization?

Example

An error message like "Invalid email address" needs to render as "अमान्य ईमेल पता" for Hindi-speaking users.

Approach

Create locale-specific message property files — messages_en.properties, messages_hi.properties — with the same keys, translated per language.

Fix

Use a LocaleResolver to decide the user's language from the request header, user profile setting, or a request parameter (e.g. Accept-Language: hi), and let Spring pick the matching properties file automatically when resolving message keys.

Q37

One API needs to handle a very high number of concurrent requests without blocking threads. When will you choose Spring WebFlux, and what mistakes will you avoid?

Example

A notification-streaming endpoint needs to hold tens of thousands of concurrent long-lived connections — a traditional thread-per-request model would exhaust threads fast.

Approach

Choose WebFlux when the API handles many concurrent requests, or mostly waits on external systems (external API calls, streaming data, real-time data) rather than doing CPU-bound work. Use Mono for zero-or-one results and Flux for multiple/streamed results.

Fix
  • Avoid blocking calls inside a reactive chain — no plain JDBC calls, use reactive drivers (R2DBC) where possible.
  • Never use Thread.sleep() inside a reactive pipeline.
  • Avoid calling .block() unnecessarily — it defeats the purpose of being non-blocking.

Rule of thumb: only adopt WebFlux when the full call chain can realistically stay non-blocking end-to-end — mixing in blocking code negates most of its benefit.
